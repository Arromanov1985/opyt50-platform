# СТАЖНО: автоматические повторные попытки рабочих писем (0.5.5)

## Зачем

В прежней версии приложение записывало событие в `email_outbox`, но
вызывало SMTP до фиксации бизнес-транзакции; при сбое SMTP повторной
отправки не было. Сам факт записи уведомления ошибочно можно было принять
за успешную доставку.

Теперь пять **новых** рабочих событий ставятся в отдельную устойчивую
очередь, атомарно с изменением бизнес-данных:

- `new_application` — новый отклик работодателю;
- `invitation` — приглашение соискателю;
- `invitation_response` — ответ работодателю;
- `contact_opened` — подтверждение открытия контакта соискателю;
- `application_status` — отдельное изменение статуса.

Старая таблица `email_outbox` остаётся историческим журналом создания
уведомлений; **старые записи не импортируются и не рассылаются заново**.
Новая таблица `email_delivery_jobs` создаётся автоматически при запуске
через безопасный `CREATE TABLE IF NOT EXISTS` на SQLite и PostgreSQL,
без изменения исходной таблицы или удаления существующих данных.

## Жизненный цикл уведомления

1. Бизнес-операция создаёт `email_outbox` и `email_delivery_jobs` в одной
   транзакции. При откате операции обе записи откатываются, письмо не уходит.
2. Фоновый обработчик читает только **уже сохранённые** записи и атомарно
   захватывает письмо с ограниченной по времени арендой (`lease`). Если
   приложение запущено в нескольких экземплярах, один и тот же активный
   `lease` не может одновременно захватить другой экземпляр.
3. Обработчик вызывает штатный SMTP с обязательным TLS и аутентификацией
   согласно текущим настройкам.
4. При ответе «принято» фиксируется `accepted`. Это **не означает
   получение письма адресатом во «Входящих»**.
5. При сбое попытки следуют паузам **30 секунд → 2 минуты → 10 минут**.
   Максимум **4 SMTP-попытки** (первичная и три повтора); затем статус
   `exhausted`. Если SMTP вообще не настроен, попытки не сжигаются.
6. Если приложение перезапустилось во время отправки, через 120 секунд
   незавершённая аренда может быть повторно захвачена. В случае утраты
   последней аренды после четвёртой попытки очередь помечается
   `exhausted`, а пятая отправка не производится.

**Техническая гарантия:** доставка типа *at least once*, а не
*exactly once*. Если почтовый сервер принял письмо, но приложение
перезапустилось до записи `accepted`, повторная попытка может отправить
дубликат. Полностью исключить такие случаи без подтверждения от внешнего
SMTP-провайдера и его механизма идемпотентности невозможно.

## Что принципиально не повторяется

- Ссылки восстановления пароля и подтверждения email.
- Одноразовые коды MFA и другие чувствительные уведомления.
- Уже существовавшие строки `email_outbox` до установки релиза.

Эти письма продолжают отправляться существующим непосредственным способом.
Их хранимые версии могут быть редактированы/обезличены для безопасности:
по ним **нельзя** повторно строить письмо с секретным токеном.

## Администратор и эксплуатация Timeweb

После публикации релиза войти в кабинет администратора и открыть
**«Проверка служебных писем» → «Повторная отправка рабочих уведомлений»**:

| Показатель | Значение |
| --- | --- |
| В очереди | Ещё не было первой попытки |
| Повторная попытка | SMTP не принял письмо, запланирован следующий запуск |
| Отправляются | Письма захвачены обработчиками |
| Принято SMTP | SMTP ответил положительно; получение адресатом неизвестно |
| Исчерпали попытки | Автоматические отправки завершены неуспешно |

Не показываются почтовые адреса, телефоны, тексты сообщений, секреты и
токены. Для аварийного отключения автоматического обработчика можно
задать **`OPYT50_MAIL_WORKER_ENABLED=0`** и повторно запустить приложение.
Это не удаляет задания; отправка возобновится после включения, если
сохранились сроки аренды и ещё доступны попытки. По умолчанию обработчик
включён и проверяет очередь приблизительно раз в 5 секунд.

Если число `exhausted` растёт: проверить SMTP/TLS и ограничения отправки
провайдера. Не запускать неконтролируемую массовую повторную рассылку:
для exhausted требуется отдельная проверка причины и безопасное ручное
решение. В релизе 0.5.5 **нет кнопки массовой переотправки**.

## Приёмка

- CI: тесты пауз, исчерпания 4 попыток, двух конкурентных обработчиков,
  восстановления аренды, отсутствия повторных писем со старыми токенами,
  отката транзакции и защиты от повторной отправки исторических записей.
- API/browser CI: цепочка `отклик → приглашение → согласие → открытие
  контакта` и счётчики администратора.
- PostgreSQL integration: проверка совместимости новой таблицы с рабочим
  механизмом запуска миграций.
- Реальные внешние письма CI **не отправляет**. После успешного деплоя
  Timeweb приёмка с двумя подконтрольными почтовыми ящиками остаётся
  отдельным шагом.

Особенно важно: работающая основная база данных на Timeweb должна быть
внешней PostgreSQL; файловая SQLite внутри сменяемого контейнера не может
обеспечить устойчивость после деплоя.
