# Перенос ОПЫТНО.РФ: SQLite → PostgreSQL (один снимок, без переключения сайта)

**Важно:** сейчас новый PostgreSQL находится в приватной сети `opytno-private`, а старый `opytno-preview` — вне её. Нельзя выполнять миграцию напрямую из старого контейнера к адресу `192.168.0.4`. Нужен изолированный исполнитель в приватной сети с доступом к корректному SQLite-снимку. Не пересоздавайте старый контейнер ради миграции.

Подготовлено: `scripts/migrate_sqlite_to_postgres.py`. По умолчанию выполняется только dry-run. Применение требует `--apply` и `DATABASE_URL` через секреты Timeweb. Инструмент требует **полностью пустой целевой схемы** и откатывает транзакцию при ошибке. Не использовать его повторно поверх перенесённых данных.

## Порядок

1. Согласовать *момент заморозки записи* на старом сайте. Копия SQLite от 21 октября — устаревший снимок, не подходит для окончательного переключения, если после него были изменения.
2. Снять актуальную онлайн-копию исходной SQLite, проверить `PRAGMA integrity_check`, `PRAGMA foreign_key_check` и подсчитать все таблицы.
3. Перенести эту копию **защищённым способом** в изолированный исполнитель в приватной сети. Никогда не копировать незашифрованную базу в репозиторий, чат или логи.
4. В Timeweb задать `DATABASE_URL` для `gen_user` и базы `default_db` на `192.168.0.4:5432`, не публикуя пароль.
5. Установить `python -m pip install -r requirements-postgres.txt` в изолированном окружении.
6. Сначала выполнить `python scripts/migrate_sqlite_to_postgres.py --source /path/to/snapshot.db` и сверить счётчики с источником.
7. После проверки пустоты PostgreSQL и отдельного разрешения на запись выполнить `python scripts/migrate_sqlite_to_postgres.py --source /path/to/snapshot.db --apply`.
8. Сверить количество записей в таблицах и ограничения, запустить PostgreSQL интеграционные тесты. Не направлять реальный трафик до успешной проверки всех запросов приложения.
9. Отдельно проверить регистрацию, вакансии, отклики, приглашения, согласия, демонстрационное знакомство и устойчивость к повторным запросам; только после этого обсуждать переключение.

## Что нельзя считать завершённым
- Подготовленный генератор PostgreSQL DDL и мигратор **ещё не означают**, что FastAPI умеет работать с PostgreSQL. Сейчас приложение использует SQLite-специфичный API.
- Без реального сетевого доступа к обоим хранилищам и согласованного актуального снимка я не могу утверждать, что данные уже перенесены.
- При выполнении SQL на стороне PostgreSQL проверка ограничения уникальности сама по себе не доказывает идентичность всех значений: нужны интеграционные проверки и приёмка.
