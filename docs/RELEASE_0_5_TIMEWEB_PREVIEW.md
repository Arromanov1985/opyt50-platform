# СТАЖНО — безопасная приёмка релиза 0.5 на отдельном стенде Timeweb

**Область применения:** только открытый PR №51 и ветка
`feature/release-0.5-application-filters`. Не переключать приложение,
собранное из `main`, и не объединять PR ради предпросмотра.

## Почему отдельный стенд

В Timeweb Cloud App Platform доступны **Стенды**: из выбранной ветки создаётся
отдельная версия приложения со своим временным HTTPS-адресом. Это подходит
для открытого PR №51; закрывать и открывать PR заново не требуется.

Документация:
- <https://timeweb.cloud/docs/apps/stands>
- <https://timeweb.cloud/docs/apps/pull-request-stands>

Для уже открытого PR удобнее **ручной стенд**. Автосоздание по PR обычно
срабатывает при открытии PR, поэтому одно включение автоматизации задним
числом не следует считать подтверждением существования стенда.

## Подготовка и контроль разделения данных

1. Убедиться, что CI в PR №51 зелёный и зафиксировать его head SHA.
2. Подготовить **новую, пустую** PostgreSQL-базу (либо отдельный изолированный
   каталог/БД без доступа к рабочим данным). **Никогда не копировать
   `DATABASE_URL` рабочего приложения.** Для проверки сохранения истории и
   миграций лучше отдельная PostgreSQL, а не SQLite внутри контейнера.
3. Не переносить из основного приложения SMTP, ключи интеграций, токены,
   production session secrets и пользовательские данные. Нужные секреты
   создавать отдельно только в панели Timeweb.
4. Не включать опцию **«Автоматически передавать переменные приложения»**:
   она может передать рабочую БД и секреты в стенд. Если она уже включена,
   перед деплоем проверить все значения в настройках стенда.
5. Использовать только фиктивные аккаунты, вымышленные контакты и
   тестовые вакансии. Настоящие оплаты и письма запрещены.

## Создание вручную в панели Timeweb

1. Открыть **Timeweb Cloud → App Platform → приложение СТАЖНО → Стенды**.
2. Выбрать **«Добавить стенд»** (или форму создания, если стендов нет).
3. Имя: `stazhno-pr51-review`.
4. Ветка: `feature/release-0.5-application-filters`.
5. Выбрать последний коммит PR №51. Для воспроизводимой приёмки можно
   закрепить конкретный SHA; для автоматического обновления оставить сборку
   по последнему коммиту ветки. **Не выбирать `main`.**
6. Создать **отдельный** набор переменных окружения для стенда; не
   копировать рабочий набор. Запустить деплой и получить новый технический
   домен. Проверить в логах, что собран именно выбранный SHA.
7. После получения домена установить `OPYT50_PUBLIC_URL` и
   `OPYT50_ALLOWED_HOSTS` для **домена стенда**, обновить стенд.
8. Проверить `GET /api/health` (ожидается HTTP 200). Для главной страницы
   должна появляться HTTP Basic-защита (401 без авторизации).

### Переменные стенда

| Переменная | Режим для стенда |
| --- | --- |
| `OPYT50_ENV` | `preview` (не `prod`; отдельный тестовый контур) |
| `OPYT50_PUBLIC_URL` | Точный `https://<домен стенда>` |
| `OPYT50_ALLOWED_HOSTS` | Только имя технического домена стенда |
| `OPYT50_COOKIE_SECURE` | `1` |
| `OPYT50_PREVIEW_USERNAME` | `review` (или отдельное уникальное имя) |
| `OPYT50_PREVIEW_PASSWORD` | **Новый длинный случайный пароль**; задать только в Timeweb, не в GitHub и не в переписке |
| `OPYT50_ENABLE_DOCS` | `0` |
| `OPYT50_PREVIEW_SEED_DEMO` | `0` |
| `DATABASE_URL` | **Отдельная тестовая PostgreSQL**, не production DSN |
| `OPYT50_DB_SSLMODE` | `verify-full`, если настроена проверка сертификата; иначе минимум `require` |
| `OPYT50_SMTP_HOST` | Не задавать: не отправлять письма на реальные адреса |

**Важно:** Dockerfile в текущем репозитории запускает `uvicorn` напрямую,
а не `deploy/start.sh`. Поэтому переменная
`OPYT50_PREVIEW_SEED_DEMO=1` **не является надёжной командой для
создания демоданных в App Platform**. Для стенда создайте вымышленные
учётные записи через интерфейс (после включения защиты паролем);
локальные автоматические тесты сами создают демобазу. Не пытайтесь
запускать `scripts/seed_demo.py` против рабочей PostgreSQL.

### Что проверять вручную

- **390 / 320 px, обычный и крупный шрифт:** нет горизонтальной прокрутки,
  все кнопки и текст доступны; клавиатурный фокус сохраняется при выборе
  раздела кабинета.
- **Гость:** поиск вакансии → просмотр условий → «Откликнуться» → вход.
  После входа открывается выбранная вакансия, но отклик **не отправляется
  автоматически**.
- **Новый кандидат:** регистрация → короткий профиль → сохранение →
  выбранная вакансия. Нажатие «Откликнуться» должно быть самостоятельным.
- **После отклика:** в той же вакансии появляется постоянный статус и
  ссылка в историю, без кнопки повторной отправки.
- **Работодатель:** видит отклик и профессиональную часть профиля, но
  **не видит имя и контакты** до отдельного согласия.
- **Соискатель:** приглашение выводится выше обычных рекомендаций;
  название компании, условия и чекбокс согласия доступны до истории.
  Без галочки «Да, интересно» не отправляет согласие.
- **После согласия:** работодатель ещё не получает контакты
  автоматически; он отдельно открывает контакт (тестовая операция).
- **После открытия:** кандидат видит «Знакомство состоялось», работодатель
  — действия написать/позвонить и фиксацию итога. Положительный итог
  **не считается доказательством трудоустройства**.

Все перечисленные сквозные сценарии дополнительно проверяются браузерными
тестами CI на отдельной фиктивной локальной БД; тесты CI **не заменяют**
приёмку опубликованного стенда.

## Что запрещено делать до принятия решения

- Переключать существующее опубликованное приложение Timeweb на feature-ветку.
- Изменять DNS `stazhno.ru` или делать merge PR №51 в `main`.
- Подключать тестовый стенд к рабочей БД или рабочей SMTP-рассылке.
- Тестировать на настоящих резюме, телефонах и переписках пользователей.
- Объявлять релиз опубликованным только потому, что `/api/health` отвечает 200.

После приёмки зафиксировать URL стенда (без паролей), SHA, результаты
мобильной проверки и скриншоты в PR №51 / issue №14. Отдельное решение о
слиянии в `main` и публикации остаётся за владельцем продукта.
