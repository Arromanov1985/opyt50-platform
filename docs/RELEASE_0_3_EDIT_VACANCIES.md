# ОПЫТНО.РФ — редактирование опубликованных вакансий (Release 0.3)

## Цель
Работодатель может поменять опубликованную вакансию без повторной публикации и без потери откликов, приглашений, согласий и демонстрационных знакомств. Все изменения сначала проходят предпросмотр.

## Реализация и ограничения
1. В разделе **«Мои вакансии»** у каждого объявления есть кнопка **«Редактировать»**. Она открывает уже известную пошаговую форму с заполненными полями.
2. Для вакансий нового формата обязанности, требования и условия открываются в трёх отдельных полях. **Старые вакансии с произвольным текстом остаются в одном поле** — система не пытается угадать структуру, переставлять блоки или сокращать существующий текст.
3. Основные сведения (название, город, оплата, график, занятость, навыки) доступны для изменения. Статус объявления «Открыта/Закрыта» управляется только существующими отдельными кнопками.
4. Перед сохранением обязательно нажать **«Посмотреть вакансию»**. Любое изменение после предпросмотра снова блокирует кнопку **«Сохранить изменения»**.
5. После подтверждения браузер отправляет `PATCH /api/employer/vacancies/{id}`. **Не отправляется POST создания вакансии**. Идентификатор, время создания и внешний ключ откликов остаются прежними.
6. **API требует принадлежности вакансии работодателю**: чужую вакансию изменить нельзя. Проверяются длина текста, типы данных, зарплата и допустимые варианты графика/занятости.
7. **Защита от устаревшей версии.** В закрытом кабинете работодателя API возвращает `revision` — SHA-256 отпечаток текущих значимых полей вакансии. `PATCH` содержит `expected_revision`; если вакансия менялась в другой вкладке или её статус изменился, сервер отвечает HTTP 409 и требует переоткрыть редактор. На уровне SQL изменения защищены сравнением предыдущих полей.
8. Структура таблиц SQLite не меняется; `vacancies.id`, `created_at`, `status`, все `job_applications`, `invitations` и их согласия сохраняются. Тексты, введённые работодателем, отображаются как текст, без исполнения HTML.
9. При выходе без сохранения действует **«Отменить редактирование»** — никаких изменений в базе.
10. Важно: ранее откликнувшиеся соискатели **не получают автоматического уведомления**, если условия вакансии изменились. Это явно показано в интерфейсе и требует отдельного решения перед реальным запуском.

## Приёмочные критерии
- Сохранение изменений в одной вакансии не создаёт дубля; ID не меняется.
- Изменённая зарплата/условия видны в публичной карточке после сохранения, старые отклики и приглашения остаются.
- Только владелец может отредактировать вакансию. Чужая вакансия → 404, кандидат → 403.
- Некорректная зарплата и пустой заголовок → 422; устаревшая ревизия → 409.
- Закрытая вакансия после редактирования **не открывается автоматически**.
- Старое описание произвольного формата редактируется без потери строк и без принудительного перевода в три поля.
- Кнопка сохранения неактивна до предпросмотра; изменение отменяет предпросмотр; повторная проверка необходима.
- Редактор с включённым крупным текстом и на ширине 390px не уходит в горизонтальную прокрутку.
- API и браузерные регрессионные тесты релиза 0.2.1.4 и задач релиза 0.3 пройдены.
- Затем отдельная ручная приёмка на текущем тестовом Timeweb. Без неё ветку не сливать.

## Управление релизом
- Разработка: `feature/release-0.3-edit-vacancies`, основание: `feature/release-0.3-employer-vacancy-preview`.
- `main` не изменять без отдельного подтверждения.
- Timeweb вручную не переключать без согласования.
- Только вымышленные данные. Реальные персональные данные, платные сервисы, email и платежи не подключать.

## За рамками задачи
История изменений вакансии, автоматические оповещения об изменении условий, подтверждение кандидатами новых условий и миграция на постоянную базу — отдельные этапы. До производственного запуска эти требования нужно отдельно проработать.
