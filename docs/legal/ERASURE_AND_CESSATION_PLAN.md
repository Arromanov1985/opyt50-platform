# СТАЖНО.РУ — план прекращения обработки и удаления данных (безопасный тестовый контур)

**Дата:** 19 ноября 2026 года. **Оператор:** ИП Иванов Иван Иванович, тестовые реквизиты, регистрация ИП не подтверждена.  
**Статус:** DRAFT / NOT APPROVED / **NO AUTOMATED ERASURE**. Связанные записи не удаляются кодом этого этапа.  
**Реализация:** `app/privacy_disposal.py`, `privacy_rights.py`, администраторская панель, PR #99.  
**Правовые основания/сроки:** уточнить по действующему законодательству РФ на дату юридической приёмки. Эта инструкция не является юридическим заключением.

## 1. Почему нельзя просто выполнить `DELETE FROM users`

В схеме СТАЖНО много связей с `ON DELETE CASCADE` и внешними ссылками. Для **кандидата** удаление может затронуть профиль, резюме, отклики, историю откликов, приглашения, согласия, избранное, уведомления и устройства. Для **работодателя** — вакансии, черновики, отклики **чужих кандидатов**, приглашения, сведения о раскрытии контактов, жалобы и историю изменений. Некоторые журналы и доказательства имеют отдельные обязанности по хранению, а данные уже могут находиться в почтовом сервисе, бэкапах или у получателя.

Физическое удаление без инвентаризации может нарушить права других лиц и уничтожить необходимые доказательства — **запрещено до отдельного юридического решения и технического дизайна**.

## 2. Что сделано в PR №99

1. `GET /api/admin/privacy-requests/{request_key}/impact` — **только для администратора**. По запросу `deletion` или `stop_processing` считает связанные записи из фиксированных SQL-запросов. Возвращает только количество по категориям (без имён, email других лиц, текстов вакансий и токенов).
2. Счётчики для всех ролей: сессии, устройства, восстановительные токены, юридические подтверждения, обращения, события безопасности, адресованные письма и почтовые связи.
3. Для кандидата: профиль, резюме, квалификация, отклики и история, избранное, приглашения, ранее раскрытые контакты, уведомления об изменениях вакансий, поданные жалобы.
4. Для работодателя: карточка компании, вакансии/черновики, затрагиваемые отклики кандидатов, приглашения и раскрытые контакты, обновления вакансий, жалобы на компанию.
5. `GET/POST /api/admin/privacy-requests/{request_key}/disposition-review` — отдельный **ручной чек-лист** и история его изменений в таблицах `privacy_disposal_reviews` и `privacy_disposal_review_actions`, для SQLite и PostgreSQL.
6. **Семь обязательных подтверждений**: личность; законное основание; сроки хранения; связанные данные и чужие права; получатели; резервные копии/подрядчики; **реальное исполнение вручную вне системы**.
7. Результат `completed` / `fulfilled` для `deletion` или `stop_processing` больше не может быть записан без всех семи отметок, ранее начатого рассмотрения и подтверждения отправленного ответа. Для мотивированного отказа действует отдельный процесс.
8. В админ-панели «Оценить последствия»: только счётчики, риски и чек-лист. Никаких кнопок физического удаления или массовой выгрузки.

**Ограничение:** администратор может отметить чекбокс неправдиво — программа не может подтвердить внешнее действие. Это организационная ответственность владельца. Не использовать наличие семи галочек как юридическое заключение.

**Защита от устаревшей оценки:** вместе с каждой ручной проверкой сохраняется SHA-256-отпечаток **только агрегированных счётчиков** связанных данных. При попытке закрытия система заново считает записи; если их количество изменилось после последней проверки, прошлые отметки перестают разрешать завершение запроса. Администратор повторно изучает последствия и сохраняет новый чек-лист. Это не криптографическое доказательство удаления: изменения содержимого при неизменном количестве записей могут остаться незамеченными, а внешние системы не охвачены.

## 3. Матрица проверки последствий (не исчерпывающая)

| Область | Где искать | Что решает оператор |
| --- | --- | --- |
| Профиль / резюме | `candidate_profiles`, `candidate_resume_details`, `candidate_resume_qualifications` | Разрешённый объём удаления/обезличивания и срок |
| Отклики и история статусов | `job_applications`, `application_events` | Право кандидата и интересы работодателя, уведомления |
| Вакансии и черновики | `vacancies`, `vacancy_drafts`, `vacancy_updates` | Что делать с откликами кандидатов, сроками размещения |
| Приглашения и контакты | `invitations`, `invitation_outcomes` | Ранее открытые контакты нельзя «отозвать назад» из памяти получателя, можно оценить отдельные обязанности |
| Подтверждения документов | `legal_acceptance_records` | Возможность и срок хранения доказательств |
| Обращения и действия админа | `privacy_rights_requests`, `privacy_rights_admin_actions`, `privacy_disposal_reviews` | Правомерность хранения аудита после удаления аккаунта; текущий `ON DELETE CASCADE` **не годится как утверждённый регламент** |
| Уведомления | `email_outbox`, `email_delivery_jobs`, `email_delivery_recipients` | Подавление ещё не отправленных уведомлений, отложенные очереди, хранение писем у провайдера |
| Сеансы и безопасность | `sessions`, `account_devices`, `security_events`, `email_tokens` | Какие технические события сохранить и как исключить дальнейшие обращения |
| Внешние обработчики | Timeweb, PostgreSQL, бэкапы, SMTP, мониторинг, CDN | Фактическая локализация, договоры, сроки резервных копий, удаление и уведомления |
| Получатели | работодатели, которым переданы контакты | Уведомления по применимому праву и ограничения последующей обработки |

## 4. Шаги ручной юридической процедуры

- **A. Установить личность заявителя** минимально достаточным способом. Сеанс аккаунта не всегда достаточен для сложного случая.
- **Б. Классифицировать запрос**: удаление либо прекращение конкретной обработки; идентифицировать цель, категории сведений и имеющиеся основания.
- **В. Открыть предварительную оценку** по конкретному запросу. Счётчики — моментальный срез, а не неизменяемый список объектов.
- **Г. Проверить основания для сохранения** данных, интересы и права других лиц, договорные и иные законные сроки. Составить перечень фактически затронутых систем.
- **Д. Проверить передачу данных** работодателям, состояние почтовых заданий, журналов и бэкапов; определить разрешённые меры.
- **Е. Согласовать исполнимый план с юристом** и владельцем ИП: временные ограничения доступа, необходимые сохраняемые доказательства, режим обезличивания и исключения, последовательность технических работ и проверки результата.
- **Ж. Выполнить одобренные действия** в контролируемой среде оператором/уполномоченным специалистом, при необходимости с резервной копией и независимым контролем. **Никаких универсальных SQL-скриптов физического удаления пока нет.**
- **З. Отдельно ответить заявителю**, только затем зафиксировать все чекбоксы и закрыть обращение в панели. Подтверждение действия в UI не выполняет физического удаления.

## 5. Что ещё блокирует реальное удаление

- Достоверные реквизиты и статус ИП, юридическое утверждение целей/сроков, работающая почта.
- Юридически разрешённая матрица уничтожения/обезличивания для каждой категории и каждого получателя.
- Техническое решение для сохранения необходимого минимального аудита без привязки к удаляемому аккаунту, иначе каскадное удаление уничтожит журнал рассмотрения.
- Подавление повторных служебных писем и фоновых заданий после прекращения обработки.
- Процедура резервных копий, внешних систем, исправления уже предоставленных контактов и проверки результата.
- Утверждение режима ограниченного тестирования, правил branch protection, юристом и владельцем конкретного релиза.

**Не считать завершение запроса в тестовом интерфейсе доказательством уничтожения ПД.** До утверждения юридических требований функциональность остаётся в отдельной ветке.
